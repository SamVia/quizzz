## Master Cheat Sheet: Service Interface Design

### 1. Fundamentals of Software & Interface Design

* In the software life-cycle, Interface Design is an integral part of the software design phase.


* The architecture definition consists of modules and their respective interfaces.


* Problems addressed during the software design phase include:


* How to partition the system into modules and determine granularity.


* How to properly design interfaces.


* How to deploy modules onto hosts in a distributed software environment.




* While software design is a creative activity, it relies on fundamental principles.


* **Basic Principle:** Information hiding implies a clear separation between the interface and its implementation.



### 2. Partitioning Principles & Granularity

* **Partitioning Principles:**
* Maximize internal cohesion within modules.


* Minimize coupling between modules.


* Foresee and favor future changes (ensuring openness to changes).


* Favor reuse (ensuring flexibility).


* In distributed environments, dynamically balance the load across various distributed sub-systems.




* **Choosing the Granularity Level:**
* Finding the right trade-off is mandatory.


* Too fine grain partitioning negatively impacts performance and increases coupling.


* Too coarse grain partitioning negatively impacts internal cohesion, flexibility, and reuse.





### 3. Interface Design Rules and Best Practices

* Designers must produce a formal description of interfaces.


* Interfaces must strictly align with partitioning principles:


* **Information Hiding:** Expose no more than what is strictly needed by the service client.


* **Minimize Coupling:** Maintain high internal cohesion and limit the number of interactions required to access offered services.


* **Favor Re-use:** If the interface is object-oriented, inheritance should be adopted.




* **Additional Best Practices:**
* Foresee all particular cases and exceptions to favor debugging and build a robust, secure system.


* Prefer idempotent methods to limit uncertainty regarding the results of distributed calls.


* Limit the number of interactions and the size of messages, as fragmentation, buffering, and processing time adversely affect performance.


* Allow clients to select exactly what and how much data to receive/send to avoid transmitting unnecessary data.





### 4. Interface Design Approaches

* **Method Centric:**
* Utilizes a fixed endpoint akin to a classical programming language approach.


* Design revolves around operations and their input/output arguments.




* **Message Centric:**
* Utilizes a fixed, single-operation interface (e.g., `send(Message)`).


* Design revolves around messages and endpoints.




* **Constrained (e.g., REST):**
* Sits half-way between method and message centric approaches.


* Utilizes a fixed, multiple-operation interface (e.g., REpresentational State Transfer).


* Design revolves around endpoints, allocation of operations, and input/output arguments.




* **Universality:** While the design approach influences syntax and understandability, most design principles apply universally across approaches because they map to underlying service features.


* Fault conditions, for example, can be mapped as separate messages, fields of a single message, or predefined error codes, but must always be considered in the design.



### 5. REST-Specific Issues & Best Practices

* Designing a RESTful API goes beyond general principles; it requires adhering strictly to REST constraints.


* Issues to consider include organizing/designing resources, mapping conceptual operations to methods, and providing documentation and API self-description capabilities.


* Design patterns exist to guide this, noting that not every "REST API" is fully REST.



### 6. Designing RESTful APIs: The 8-Step Process

* **Step 1: Object Model Definition**
* Establish the conceptual relationships of your entities.




* **Step 2: Designing Resources**
* Start with a conceptual resource design independent of URIs and representations.


* Ensure resources correspond to single entities or collections of the same type in a hierarchical organization (forest).


* Resources must be unique, but different resources can represent related or overlapping entities.


* Do not confuse resources (nouns) with actions (verbs).


* Use a coarse granularity level as far as possible.




* **Step 3: Representing Resource Relations**
* Use mechanisms like references (hyperlinks) or resource nesting.


* *1 to Many:* Either the "Many" data model includes a reference to the "1", or instances of the "Many" are nested into the "1" (better when not autonomous).


* *Many to Many:* Data models can include bidirectional references, or the relation elements themselves (the pairs) can be represented as new resources.




* **Step 4: Mapping Resources to URIs**
* Conventions make the API self-describing.


* Use plural names for collections, and singular for non-collections.


* Use URLs that reproduce hierarchical relationships.


* (Note: According to HATEOAS, URLs should theoretically be opaque, though this is debated).




* **Step 5: Defining Resource Representations**
* Define an abstract data model (UML, schema) for each resource's state.


* Define representations (different content types).


* Hyperlinks can be represented as Link objects (Atom: `"link": {"rel":"come_from","href":"/country/italy"}`), Objects with hrefs, or simple href strings.




* **Step 6: Mapping Operations**
* Find matching resource(s) and HTTP method(s) for each offered operation; missing matches may indicate missing resources.


* Define how methods are invoked (query parameters, request headers, body contents).


* Define possible results (status codes, response headers, and body contents).




* **Step 7: Getting HATEOAS**
* Add hyperlinks to resource data models or response HTTP link headers (e.g., `Link: [http://example.com/users/12](http://example.com/users/12); rel=next`).


* Clients should never "build" hyperlinks, only follow provided ones.


* Use standard conventions: "self" points to the resource itself, "next" navigates to the next in a sequence.




* **Step 8: Documenting the REST API**
* Design choice tables form the basis for documentation.


* OpenAPI is a straightforward tool for this.


* Include JSON schemas in `#components/schemas`, document resources by tags, and use paths to document URLs and operations.





### 7. Performance & Concurrency Controls

* **Avoiding Large Messages:** Use query parameters to let users decide what to get, employ paging, and use references instead of full representations.


* **Conditional Requests:** Let clients specify execution conditions via headers:


* `If-Modified-Since`: Executes if Last Modified date is more recent than the header value.


* `If-Unmodified-Since`: Executes if Last Modified date is older/same as the header value.


* `If-Match`: Executes if resource Etag matches a listed value.


* `If-None-Match`: Executes if resource Etag differs from all listed values.




* **Conditional Use-cases:**
* *Cache Management:* Client sends `GET` with `If-Modified-Since`. Server returns `304 Not Modified` if unchanged, or `200 OK` with a new `Last-Modified` if changed.


* *Read-Update Race Conditions:* Clients `GET` a resource, compute updates, and `PUT` with `If-Unmodified-Since`. If another client updated it first, the server returns `412 Precondition Failed` to prevent lost updates.


* *PUT (Create) Race Conditions:* Use `If-None-Match: *` to prevent multiple clients from creating the same resource; secondary creators receive `412 Precondition Failed`.

### Practical Exercises

#### Exercise 1: Bank Account Operations

**Scenario:** Service enabling bank account operations (read info, deposit, withdraw with reducible flag).

Method-centric Design (1st try Java Code):

```java
public interface AccountReader {
    public Account getAccountInfo (String id)
    throws UnknownAccountIdException;
}

public interface AccountUpdater {
    public void addDeposit(
        String id,
        float amount,
        String description)
    throws UnknownAccountIdException;

    public float addWithdrawal(
        String id,
        float requestedAmount,
        boolean reducible,
        String description)
    throws UnknownAccountIdException,
           NoAvailabilityException;
}

```

Method-centric Design (2nd try Java Code - improved with Transaction IDs):

```java
public interface ImprovedAccountUpdater {
    public void addDeposit(
        String id,
        float amount,
        String description,
        String transId)
    throws ReplicatedTransIdException,
           UnknownAccountIdException;

    public float addWithdrawal(
        String id,
        float requestedAmount,
        boolean reducible,
        String description,
        String transId)
    throws ReplicatedTransIdException,
           UnknownAccountIdException,
           NoAvailabilityException;
}

```

REST Service Design (2nd try):

* **Resources:** `accounts` (set of all), `accounts/{id}` (single), `accounts/{id}/operations` (set of all ops), `accounts/{id}/operations/{tid}` (single op).


* **Operations Mapping:**
* `GET accounts/{id}` -> 200 OK (Resp: account) | 404 Not found.


* `PUT accounts/{id}/operations/{tid}` (Req: operation) -> 201 Created (Resp: operation) | 409 Conflict (Resp: reason) | 404 Not found.





#### Exercise 2: Bibliography REST API Design

**Scenario:** Remote management of a bibliography (searching, populating, updating).

* **Designing Resources:** `biblio` (main), `items`, `{id}` (unique item), `journals`, `{issn}`, `issues`, `{iid}`. Also `citing` and `cited` for relations.


* **Mapping to URIs:** `biblio/items`, `biblio/items/{id}`, `biblio/items/{id}/citing`, `biblio/journals/{issn}/issues/{iid}`.


* **Mapping Operations (Search):**
* `GET biblio/items` (Query params: keyword, type, beforeInclusive, afterInclusive) -> 200 OK (Resp: filtered items).


* `GET biblio/items/{id}` -> 200 OK (Resp: item) or 404 Not Found.




* **Mapping Operations (Update/Modify):**
* `POST biblio/items` (Req body: item) -> 201 Created (Resp: item) or 400 Bad Request.


* `PUT biblio/items/{id}` (Req body: item) -> 204 No Content, 400 Bad Request, or 404 Not Found.


* `DELETE biblio/items/{id}` -> 204 No Content or 404 Not Found.


* `POST biblio/items/{id}/citing` (Req body: item) -> 204 No Content, 400 Bad Request, 404 Not Found, or 409 Conflict.
