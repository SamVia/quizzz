## Master Cheat Sheet: Remote Procedure Call (RPC)

### Definition and Core Concept

* **Remote Procedure Call (RPC)** is the mechanism that transfers the local procedure call concept into a distributed environment.


* In this model, the `main` program executes on one process (e.g., process 1), while procedure `A` executes on a second process, and procedure `B` executes on a third.


* The primary reference for this topic is "Distributed Systems" by Van Steen and Tanenbaum (Chapter 4.2), as taught by Riccardo Sisto at Politecnico di Torino.



### Examples of RPC Implementations

* **SUN RPC (ONC):** Specifically designed for the C Language.


* **JAVA RMI:** Native to the Java Language.


* **Other implementations:** CORBA, Web services, The Web (REST), and gRPC.


* These implementations provide distributed objects, distributed services, and distributed resources independent of the programming language.



### The RPC Model Architecture

* **Client Process:** Contains the client routines and the **client stub**.


* **Server Process:** Contains the server routines and the **server stub (skeleton)**.


* **Call Flow:** A local procedure call initiates from the client routines to the client stub, passes through local OS/network protocols, travels across the network to remote OS/network protocols, and reaches the server stub, which makes a local procedure call to the server routines.



### The RPC Middleware

* **Language-based support (Single language solution):** RPC is integrated as a language feature (e.g., Java RMI), utilizing language-specific data serialization.


* This provides high transparency but is restricted to single-language applications.




* **Stub Generation (Multi-language solution):** Uses an **Interface Definition Language (IDL)**.


* The IDL generates both the client stub and the server stub, allowing interoperability across multiple languages.





### Issues Handled by RPC Middleware

* **Heterogeneity:** Caller and callee may use different languages or hardware/software platforms, necessitating parameter and return value conversion known as **marshaling/unmarshalling**.


* **Distributed Processes:** Caller and callee operate on different hosts/processes.


* The server must be located before a call can be issued (dynamic linking).


* The server must synchronize multiple incoming remote calls.


* Rules must define if and how arguments can be passed by reference, given that the processes have disjoint address spaces.




* **Partial Failure:** Network outages or server crashes are possible and require dedicated management.



### Managing Partial Failure and Call Semantics

* Remote semantics differ fundamentally from local semantics because a remote call may fail (due to server crashes or network outages) or execute more than once (due to message duplication).


* RPC middleware can only partially handle these issues; programmers must be aware of them.


* Returns are generally categorized as **successful** or **unsuccessful**.



#### Semantic Guarantees

* **At Least Once Semantics (Typical UDP):**
* The RPC protocol handles response-to-request association and manages retransmissions.


* A successful return guarantees the procedure executed at least once.


* An unsuccessful return provides no guarantee (executed 0 or more times).


* Requires **idempotent procedures** (procedures not sensitive to the number of executions, e.g., writing at a specific offset rather than appending).




* **At Most Once / Exactly Once Semantics:**
* The client is guaranteed the procedure executes at most once regardless of conditions.


* A successful return provides **exactly once** semantics.


* An unsuccessful return provides **at most once** semantics.


* **TCP Implementation:** Associates responses to requests natively via the connection.


* **UDP Implementation:** Requires explicit response-request association, retransmission management, and duplicate checking on the server side.





### Security and Performance

* **Security Requirements:** Access control, authentication, confidentiality, and integrity.


* **Performance Issue:** A remote call is orders of magnitude slower than a local procedure call.



### RPC Interaction Paradigms

* **Classical (Synchronous) RPC:** The client waits for the server.


* Request includes: Procedure identification and input parameters.


* Response includes: Success/Failure indication and return value/output parameters (or exceptions).




* **One-Way (Asynchronous) RPC:** The client does not wait for a response.


* There are no output arguments, no return values, and no exceptions.




* **Two-Way Asynchronous RPC:** The client makes a request but does not block/wait.


* A callback mechanism manages the response when it arrives from the server.




* **RPC with Streaming:** Any flavor of RPC can use a stream of messages for the request, the response, or both, instead of a single discrete message.



### RPC vs. Sockets APIs

* **Sockets APIs:** Provide only raw communication services.


* The programmer must implement data encoding and interaction protocols (e.g., partial failure management).


* Emphasis is heavily on communication rather than application logic.


* Primarily used to build custom application-level protocols or middleware itself.




* **Developing on RPC:**
* Applications are written similarly to normal monolithic code, though the programmer must remain aware of distributed interaction consequences.


* Allows developers to focus strictly on application logic rather than low-level communication.




* **Service-Oriented Development:**
* Applications are built as combinations of services interacting via RPC.


* Services act as simple, reusable components.


* Scaling out is easily achieved by instantiating multiple service instances based on request volume.





### Practical Exercises

**Exercise 1: Designing an Idempotent Function**

* **Scenario:** You need to design an RPC function to add items to a user's log file over a UDP transport with "At least once" semantics.
* **Problem:** If the message is duplicated due to a network delay, the server might append the same log entry twice.
* **Step-by-Step Solution:**
1. Do not use `append(log_entry)`.


2. Instead, track the file offset on the client side.
3. Implement the remote procedure as `write(log_entry, offset_k, file_Y)`.


4. If the call executes multiple times, it simply overwrites the exact same data at the exact same offset, rendering the operation idempotent.
