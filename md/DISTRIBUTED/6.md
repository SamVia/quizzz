## HTTP/2 and gRPC Master Cheat Sheet

### Evolutions of HTTP for Efficiency and Performance

* **HTTP/2**: Optimized for networks with low error rates, such as within data centers.


* **HTTP/3**: Optimized to reduce latency for long-distance or high error rate connections.


* **Semantics**: HTTP/2 and HTTP/3 maintain the same semantics as HTTP/1.1.


* **Impact on REST APIs**: There is no impact on existing REST APIs; they can be smoothly ported to HTTP/2 and HTTP/3 because only the data encoding and use of transport protocols are different.



### TCP/HTTP/1.1 Performance Issues

* **High Latency**: Establishing connections suffers from high latency due to multiple round-trip times (RTT).


* HTTP requires 2 RTT (SYN $\rightarrow$ SYN+ACK $\rightarrow$ ACK+Req $\rightarrow$ Resp).


* HTTPS requires 3 RTT (SYN $\rightarrow$ SYN+ACK $\rightarrow$ ACK+ClientHello $\rightarrow$ ServerHello $\rightarrow$ Finished+Req $\rightarrow$ Finished+Resp).




* **Multiplexing limitations**: Multiplexing requires opening multiple separate TCP connections.


* **Encoding**: Character encoding is inefficient.



### HTTP/2 vs HTTP/1.1 Comparison

* Initially driven by Google (SPDY), then taken over by IETF (RFC 7540, 2015).



| Feature | HTTP/2 | HTTP/1.1 |
| --- | --- | --- |
| **Data Encoding** | binary

 | character-oriented

 |
| **Multiplexing** | on single TCP connection

 | on multiple TCP connections

 |
| **Compression** | header and body

 | only body

 |
| **Push Possibility** | yes

 | no

 |

### HTTP/3 Architecture

* **Transport**: TCP is replaced by QUIC + UDP (RFC 9114, June 2022).


* **Stack**: HTTP/3 runs over QUIC (+TLS), which runs over UDP, over IP.


* **Handshake**: Uses a combined QUIC+TLS handshake to reduce connection setup time.



### Adoption and Performance (2024 Stats)

* **Adoption (Page Loads)**: HTTP/1 is at 22%, HTTP/2 is at 71% (though push adoption is much lower), and HTTP/3 is at 7%.


* **Performance**:
* HTTP/3 capable web sites are over 30%.


* HTTP/2 provides a big boost over HTTP/1 on lossless connections.


* HTTP/3 performs better than HTTP/2 on long-distance or unreliable connections.





### HTTP/2: Frames and Streams

* **Frame**: A binary message exchanged by the client and server.


* **Frame Layout**: Contains a 24-bit Length, 8-bit Type, 8-bit Flags, 1-bit Reserved (R), 31-bit Stream Identifier, and Frame Payload.




* **Stream**: An independent, bidirectional sequence of frames corresponding to an ordered sequence of logical operations (Request/Response, Push).


* **Stream IDs**: Assigned by the initiator.


* Client uses odd IDs (e.g., stream 1, stream 3).


* Server uses even IDs.


* Connection control uses ID 0.




* **Stream Multiplexing**: Streams are multiplexed on a single TCP connection. The ordering of frames within each stream is preserved.


* **Flow Control**: Window-based flow control is added to regulate stream rates.



### Main HTTP/2 Frame Types

* `HEADERS`: Carries metadata/headers.


* `DATA`: Carries the payload.


* `SETTINGS`: Configuration parameters.


* `RST_STREAM`: Signals the termination of a stream.


* `PUSH_PROMISE`: Server signaling the intent to push a resource.


* `GOAWAY`: Initiates a graceful connection termination.


* `WINDOW_UPDATE`: Flow control message.



### Push Mechanism & Early Hints

* **Server Push**: A server can push additional representations, anticipating the client's requests, trading bandwidth for latency.


* *Example*: Client requests `home.html`. The server sends `home.html` and promises for linked resources (`.js`, `.css`), sending them in other server-initiated streams. The client can accept or refuse push promises.




* **Early Hints**: An alternative to server push that saves bandwidth.


* *Example*: Server sends `103: Early Hints` header for linked resources while preparing the response, prompting the client to request those desired resources directly before the `200 OK` arrives.





### Initiating an HTTP/2 Connection

* **With Prior Knowledge**: Client starts a TCP connection, sends the 24-byte preface string `PRI * HTTP/2.0\r\n\r\nSM\r\n\r\n` followed by a `SETTINGS` frame. The server responds with its preface + `SETTINGS`.


* **Without Prior Knowledge (Negotiation)**:
* **TLS-based (HTTPS)**: Uses ALPN (Application Layer Protocol Negotiation). The client requests a list of protocols, the server selects one (HTTP/2) and informs the client. The standard preface + SETTINGS exchange follows.


* **HTTP-based Upgrade (HTTP)**: The client starts an HTTP/1.1 connection with an `Upgrade` header.





```http
GET / HTTP/1.1
Host: server.example.com
Connection: Upgrade, HTTP2-Settings
Upgrade: h2c
HTTP2-Settings: <base64 encoded HTTP/2 SETTINGS>

```

* The server responds with a `101 Switching Protocols`:

```http
HTTP/1.1 101 Switching Protocols
Connection: Upgrade
Upgrade: h2c

```

* `h2c` means HTTP/2 without TLS; `h2` means HTTP/2 over TLS.



### Error Management

* HTTP/2 offers lower-level error reporting compared to HTTP/1.


* **Stream-level Errors**: Affects only a single stream. Triggers a `RST_STREAM` frame.


* **Connection-level Errors**: The entire HTTP/2 connection is compromised. Triggers a `GOAWAY` frame.


* **Main Error Codes**:
* `NO_ERROR (0x0)`

* `PROTOCOL_ERROR (0x1)`: Generic protocol error


* `INTERNAL_ERROR (0x2)`

* `FLOW_CONTROL_ERROR (0x3)`: Flow control protocol violation


* `SETTINGS_TIMEOUT (0x4)`

* `STREAM_CLOSED (0x5)`

* `FRAME_SIZE_ERROR (0x6)`



* **Safe Retries**:
* The `GOAWAY` frame indicates the highest stream number processed. Requests on streams with higher numbers can be safely retried.


* The `REFUSED_STREAM` error code in a `RST_STREAM` indicates a stream was closed before any processing occurred, making it safe to retry.





### gRPC Architecture

* An RPC mechanism built on top of HTTP/2 to exploit performance features (binary messages, header compression).


* Provides multi-language support, security management (via TLS), and "at most once" semantics.


* Supports multiple operation modes: synchronous, asynchronous, stream-oriented.


* **Stack**: gRPC $\rightarrow$ HTTP/2 $\rightarrow$ TLS $\rightarrow$ TCP.



### Protocol Buffers (Proto3)

* A system-independent data representation and IDL (Interface Definition Language) with a binary representation.


* **Basic Syntax**: C-like language (termination, blocks, comments).



```protobuf
syntax = "proto3";
service HelloService {
  rpc SayHello (HelloRequest) returns (HelloResponse);
}
message HelloRequest {
  string greeting = 1;
}
message HelloResponse {
  string reply = 1;
}

```

* **Scalar Data Types**:
* `float`, `double`: Floating point.


* `int32`, `int64`: Variable-length, inefficient for negative values.


* `uint32`, `uint64`: Variable-length unsigned.


* `sint32`, `sint64`: Variable-length signed, more efficient for negative values.


* `fixed32`, `fixed64`, `sfixed32`, `sfixed64`: Fixed-length integers.


* `bool`: boolean.


* `bytes`: byte sequence (max $2^{32}$).


* `string`: UTF-8 or 7-bit ASCII (max $2^{32}$).




* **Message Types**: Typed, named, and numbered fields.


* Fields are optional singular (0 or 1 reps, default) or optional repeated (0 or more reps).


* Absent fields return default values.




* **Enum Types**: Integers with variable-length encoding for named values. The first value *must* be 0 (default).


* **Default Values**: Numeric (`0`), bool (`false`), bytes (`empty sequence`), string (`empty string`), enum (`first value 0`), message (`unset`), repeated (`empty list`).


* **Map Types**: Associative maps. Cannot be repeated. Entry ordering is not preserved on the wire.



```protobuf
map<string, BiblioItem> items = 1;

```

* **Oneof**: A set of fields where at most one can be set (shares space on the wire). Setting one automatically unsets the others. Cannot be repeated or maps.


* **Packages & Imports**: Used for namespacing and managing large specifications. Resolved via dot notation. Declarations can also be nested.



### RPC Types in gRPC

* Classical Synchronous RPC.


* Two-Way Asynchronous RPC.


* Streaming mode (independently supported for request and response) using the `stream` keyword.



### Practical Exercises

**Exercise 1: Defining a Protocol Buffer Streaming Service**
*Scenario*: Build a bank account gRPC service where you can upload multiple transaction deposits (a stream) and get a single summary response, based on the `updateCS` structure.
*Solution*:

```protobuf
syntax = "proto3";
package it.polito.dsp.bank;

service BankAccountService {
  // Client streaming RPC
  rpc addDeposits (stream DepositRequest) returns (DepositSummary);
}

message DepositRequest {
  int32 account_id = 1;
  double amount = 2;
}

message DepositSummary {
  int32 total_deposits = 1;
  double final_balance = 2;
}

```

*Explanation*: The `stream` keyword preceding `DepositRequest` indicates the client will push multiple frames to the server over a single logical stream before the server returns the `DepositSummary`.
