## Master Cheat Sheet: Network Functions Virtualization (NFV) and Service Function Chaining (SFC)

### Service Function Chaining (SFC)

* **Definition**: SFC involves chaining different dedicated hardware appliances to provide added-value services. This practice is particularly common at the edge of the network.


* **A Chain of Network Functions**: A typical physical chain might include an ISP edge router connected to a WAN accelerator, followed by a Firewall, Network Monitor, IDS, QoS module, and finally the Internet.


* **Limitations of Physical SFC**:
* **Hardware Inefficiency**: Hardware resources (e.g., CPU, memory) are not shared optimally across services. Some appliances may suffer heavy loads while others remain unloaded.


* **Service Disruption**: Adding or removing a middlebox requires physical changes, leading to service disruption.


* **Tenant Differentiation Challenges**: Differentiating services among tenants is difficult. For example, giving only one tenant a "secure access to the Internet" requires the firewall to support complex, per-application or per-user privilege configurations.





### SDN-Based Service Function Chaining

* **OpenFlow Switch Integration**: An OpenFlow switch can connect all physical boxes together.


* **Traffic Steering**: OpenFlow rules steer traffic from specific users to the correct set of services.


* **Provisioning Models**: Rules can be pre-provisioned or instantiated on demand by a controller (e.g., valid only for a user's session duration).


* **Example Flow Rule**:
`If ip.src=X and input port=LAN goto Firewall_in`

* **Characteristics**:
* **Agility**: Routing between boxes is handled via software rather than physical rewiring.


* **Maintenance**: Cabling is only done once during initial setup.


* **Customization**: Software-based routing allows changing decisions based on various parameters, including application-layer content.


* **Remaining Drawbacks**: It remains difficult to partition a single physical appliance among multiple tenants.





### Network Functions Virtualization (NFV) Core Concepts

* **Network Function (NF)**: A functional building block within a network infrastructure. It possesses well-defined external interfaces and functional behavior (e.g., switch, router, NAT, firewall).


* **Software Network Function**: A network function implemented entirely in software. Examples include virtual machines, containers, Linux network stack configurations, and eBPF/XDP bytecode. Software NFs allow for easy cascading of "pure" network functions.


* **NFV Definition**: NFV is the capability to run any network function on standard hardware, utilizing computing virtualization for efficient resource usage.


* **Four Main NFV Components**:
1. Standard, fast Commercial-off-the-shelf (COTS) hardware (e.g., Intel servers).


2. Software-based network functions transitioning from dedicated appliances to software images.


3. Computing virtualization (e.g., Linux KVM).


4. Standard APIs, specifically relying on the ETSI framework.




* **Deployment Scenarios**:
* **Software-based (black-box) devices**: Services run on standard hardware instead of dedicated appliances (e.g., White-box Routers, Firewalls). These often use DPDK-based functions and may not use standard virtualization internally.


* **Function Modules**: Refers to pure software packages acting as data plane and control plane modules (e.g., DHCP, NAT, Rate Limiting).





### Advantages of NFV

* **Virtualization**: Users consume resources without worrying about physical location or organization.


* **Orchestration**: Enables management of thousands of devices.


* **Programmable**: Behavior can be modified dynamically on the fly.


* **Dynamic Scaling**: Systems adapt seamlessly to varying workloads.


* **Automation**: Streamlines operational workflows.


* **Visibility**: Enhances monitoring of resources and connectivity.


* **Performance**: Optimizes overall network device utilization.


* **Multi-tenancy**: Inherently supports multiple isolated tenants.


* **Service Integration**: Combines multiple functions into unified offerings.


* **Openness**: Provides full choice of service modules.



### NFV vs. SDN vs. Cloud

* **Chaining vs. General Services**: Chaining implies a stack of modules, but LAN services (DHCP, DNS, Web services) are not purely stackable. NFV must be flexible enough to model non-chained topologies.


* **NFV and Cloud**: NFV brings network services into cloud technologies. However, traditional cloud frameworks are CPU-intensive and lack advanced traffic steering, whereas NFV services are highly I/O intensive. Technologies require tuning to support the high traffic volume generated by network services.


* **NFV vs. SDN**:
* **Domains**: NFV focuses on computing. SDN focuses on network paths.


* **Complementary Nature**: NFV requires SDN for flexible traffic steering, but they operate independently; one does not depend on the other.


* **Efficiency vs. Flexibility**: SDN leverages accelerated hardware switches, making it potentially more efficient. NFV leverages standard hardware, making it currently much more flexible regarding supported applications.





### Datacenter Traffic and Scaling

* **Traffic Impact**: Deploying VMs randomly across a data center can lead to un-optimized, hairpinning paths where packets travel back and forth repeatedly to the switch.


* **I/O Optimization Requirements**: Technologies like SR-IOV, VirtIO, and Shared memory must be optimized to reduce internal server loads.


* **Scaling Types**:
* **Vertical Scaling**: Scaling up (adding resources to a server) or scaling down.


* **Horizontal Scaling**: Scaling out (adding more servers/instances) or scaling in.




* **Handling High Workloads**: VMs excel at consolidating tiny instances, but struggle with monolithic high-resource applications.


* **Solutions for High Workloads**:
1. Add a load balancer (via SDN) to split per-TCP-session traffic across independent instances.


2. Modify the application to be distributed, separating local variables from global synchronized variables.





### ETSI NFV Architectural Framework & Terminology

* **ETSI NFV ISG**: The Industry Specification Group defining the NFV architectural framework.


* **Primary Framework Components**:
* **Virtualized Network Functions (VNFs)**.


* **NFV Infrastructure (NFVI)**: Includes Virtual Compute, Virtual Storage, Virtual Network, the Virtualisation Layer, and underlying Hardware resources.


* **NFV Management and Orchestration (MANO)**.




* **Core Terminology**:
* **VNF**: Software implementation of an NF deployed in a virtualized infrastructure.


* **VNF Set**: Unspecified connectivity between VNFs (e.g., residential gateways).


* **VNF Forwarding Graph (VNF-FG)**: Service chain defining network connectivity order (e.g., Firewall -> NAT -> Load Balancer).


* **NFVI Point of Presence (PoP)**: The physical location of the NFVI.


* **VNF Manager**: Handles VNF lifecycle management (instantiation, scaling, healing, termination).


* **Virtualized Infrastructure Manager (VIM)**: Manages computing, storage, and network software resources.


* **NFV Orchestrator**: Automates coordination, deployment, and management of VNFs and NFVI.


* **VNF Descriptor**: Combines deployment behavior (required VMs, memory) and operational behavior (lifecycle operations).





### Reference Points (Interfaces)

* **VI-Ha**: Virtualization Layer to Hardware Resources.


* **Vn-Nf**: VNF to NFVI.


* **Or-Vnfm**: Orchestrator to VNF Manager.


* **Vi-Vnfm**: Virtualized Infrastructure Manager to VNF Manager.


* **Or-Vi**: Orchestrator to Virtualized Infrastructure Manager.


* **Nf-Vi**: NFVI to Virtualized Infrastructure Manager.


* **Os-Ma**: OSS/BSS to NFV Management and Orchestration.


* **Ve-Vnfm**: VNF/EMS to VNF Manager.


* **Se-Ma**: Service, VNF and Infrastructure Description to NFV Management and Orchestration.



### Practical Exercises: Deploying a Multi-Tenant Service Architecture

This exercise tracks the deployment of a multi-tenant environment using forwarding graphs as detailed in the slide scenario.

* **Step 0: System Startup**
* **Action**: A Universal Node (NFV Server) initializes with a basic L2 switch (LSI_0) and a Local Orchestrator.




* **Step 1: Graph Startup**
* **Action**: The Orchestrator automatically deploys the Authentication Graph (`Auth_NF-FG`) and ISP default services (`ISP_NF-FG`). Incoming WiFi traffic is forwarded by default to `Auth_LSI`.




* **Step 2: User Connection & Authentication**
* **Action**: An unknown user device connects. The `Auth_NF-FG` handles the unknown MAC address by assigning an IP via DHCP and redirecting web traffic via a captive portal.


* **Action**: Once authenticated, the Orchestrator instantiates a dedicated User Forwarding Graph (e.g., `BLUE_NF-FG` for user BLUE).




* **Step 3: Traffic Steering**
* **Action**: The authenticated user's traffic is explicitly routed first through their personal graph (`BLUE_NF-FG`) which contains per-tenant configurations (like specific firewall rules), and then chained into the provider's `ISP_NF-FG` before reaching the Internet.





### Future Hardware: Integrated Routers

* **Slim vs. Fat Routers**:
* **Slim Routers**: SDN predicts routers will be "slim", serving as dumb pipes. This favors low-margin vendors.


* **Fat Routers**: NFV/NSC data plane performance requires "fat" routers at the edge to handle advanced processing tasks. This retains intelligence and value in the network hardware.




* **Hybrid Integrated Platforms**: Future routers will combine general-purpose processing linecards with network processing linecards to exploit hardware accelerators. This allows mapping distinct network modules directly to the most efficient processing components at fine granularities.
